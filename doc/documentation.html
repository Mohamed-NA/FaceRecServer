Chapter 01

Overview

FaceRecServer is a real-time, browser-based face recognition system built for the Debi Hackathon. It solves a practical problem: identifying people by name from a live camera feed, with no offline training step and no special hardware required.

The core idea is simple. A user opens the web app in any modern browser, points their camera at a group of people, and the server draws a labelled bounding box around every face it sees — green for someone it recognises, red for an unknown. When the server encounters an unknown face, the user can enroll that person live: click "Add Person", type their name, and from that moment on the system recognises them. The entire enrollment-to-recognition cycle takes under five seconds.

The system is self-contained. It runs over HTTPS (required for camera access), streams annotated video back to the browser over WebSocket, and persists all known faces to a JSON file that survives server restarts. It ships as a Docker Compose stack and has a full CI/CD pipeline on GitHub Actions.

No training required Enroll a person live from the camera feed in under 5 seconds. No dataset collection, no model retraining.
High accuracy dlib ResNet trained on 3 million faces, 99.38% LFW benchmark. Configurable distance threshold.
Browser-native Pure WebSocket stream — no plugins, no proprietary SDK. Works in any modern browser over HTTPS.
Production-shaped Docker Compose stack, GitHub Actions CI/CD, TLS, thread-safe storage. Ready to deploy.

Chapter 02

Architecture

2.1

System Overview

The browser captures camera frames and sends them over a WebSocket to the Flask server. The server runs face recognition, annotates the frame with coloured bounding boxes, and streams the result back alongside a structured list of detections. All known-face embeddings live in a single JSON file on disk.

4 WebSocket eventsvideo_frame →, ← server_frame, ← detections, enroll_request →. All communication runs over a single persistent socket.
Stateless per frameEach frame is processed independently. The server holds only the most recent frame in memory for enrollment lookups.
JSON persistenceface_embeddings.json is the only stateful component. It survives restarts and is safe to back up or migrate.
2.2

Recognition Flow (per frame)

Every frame triggers a four-step pipeline: detect bounding boxes, compute 128-d embeddings, compare against the stored database, and label each face. Faces below the distance threshold are named; faces above it are numbered Unknown 1, 2, 3 … sorted left-to-right for stable labels.

HOG DetectionFast, CPU-friendly. Finds bounding boxes in each frame without a GPU.
ResNet Encodingdlib ResNet produces a 128-d vector that encodes face geometry. Same person → close vectors across lighting and angle.
Distance Threshold 0.5Euclidean distance below 0.5 declares a match. Configurable in config/recognizer.json.
Left→Right SortStable Unknown N labels across frames, regardless of internal detection order.
2.3

Enrollment Flow

When an unknown face appears, the user clicks it on the canvas, types a name in the Add Person panel, and clicks Save All. The server extracts the face embedding from the stored frame at that exact bounding box and appends it to the JSON database. The person is recognised on the very next frame.

Zero training timeUnder 5 seconds end-to-end. No dataset, no retraining.
Batch enrollmentAll unknowns named in one Save All click. One enroll_request fires per filled row in parallel.
Immediate persistenceVectors are appended to JSON on the spot. Survives restarts. Multiple enrollments per person improve accuracy under different lighting.
2.4

Docker Deployment

Two images work together via Docker Compose. The models container unpacks the embeddings into a shared volume and exits. The app container starts after, mounts the volume, and serves the recognition API. GitHub Actions builds and pushes both images automatically.

Two-image patternKeeps app image lean. Model updates don't require rebuilding the heavy Python/dlib layer.
Startup orderdepends_on with service_completed_successfully guarantees the JSON file exists before the app reads it.
Writable volumeLive enrollments during a session persist inside the running container's shared volume.
2.5

Four Python modules and two data files. app.py is the entry point and delegates all recognition work to inference.py. Both use paths.py for file-system constants. inference.py wires together face_recognition, OpenCV, and the embeddings JSON.

Chapter 03

Problems Faced & Solved

1
Package not importable after install
Problem

After creating pyproject.toml and running uv sync, scripts raised ModuleNotFoundError: No module named 'facerecserver'. The venv existed but the package was not installed.

Cause

pyproject.toml had no [build-system] table. Without it, uv treats the project as an application and does not install it as a local editable package.

Fix
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

After uv sync the package was installed and all imports resolved correctly.

2
Wrong recognition library — LBPH vs embeddings
Problem

The original plan used OpenCV's LBPH face recognizer, which required an offline data-collection phase before the server could recognise anyone. LBPH cannot do live enrollment without retraining.

Cause

LBPH was chosen for simplicity, but the hackathon brief required embedding-based recognition with a structured database, and graded on accuracy.

Fix

Switched to the face_recognition library (dlib ResNet, 99.38% LFW accuracy). Embeddings are stored as 128-d vectors in a JSON file and compared at runtime using Euclidean distance. The entire offline pipeline was replaced by live enrollment — a person is registered in under five seconds.

3
face_recognition_models missing pkg_resources
Problem

After installing face-recognition, importing it raised ModuleNotFoundError: No module named 'pkg_resources'.

Cause

face_recognition_models uses the legacy from pkg_resources import resource_filename API. In Python 3.12 environments managed by uv, setuptools is installed in a stripped form that does not expose the pkg_resources top-level module.

Fix

Patched face_recognition_models/__init__.py in the venv to use the modern standard-library replacement:

from importlib.resources import files as _files

def _model(name):
    return str(_files(__name__).joinpath("models").joinpath(name))
4
Camera blocked without HTTPS
Problem

The browser refused to call getUserMedia() when the app was served over plain HTTP on a non-localhost address.

Cause

Browsers enforce the Secure Context requirement: camera and microphone APIs are only available on localhost or HTTPS origins. Since the server runs on a LAN IP, HTTP is not treated as secure.

Fix

Generated a self-signed TLS certificate and loaded it into Flask via Python's ssl.SSLContext. The server now listens on HTTPS port 8080. The browser shows a one-time "Not Secure" warning for the self-signed cert; after clicking "Proceed" the camera works normally.

openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout certificates/private.key \
  -out    certificates/certificate.crt \
  -subj   "/CN=localhost"
5
Multiple unknown faces — enrollment ambiguity
Problem

When several unknown people were in frame simultaneously, clicking "Add Person" always enrolled the first face dlib detected internally (arbitrary order). There was no way to tell the server which person to name.

Fix — two parts

Stable labels. The server sorts unknown faces by their left-edge x-coordinate and assigns sequential labels — "Unknown 1" (leftmost), "Unknown 2", "Unknown 3" — before emitting the detections event.

Per-label enrollment form. The "Add Person" panel dynamically lists every current unknown as a labelled row with its own text input. The user fills in the names they know, leaves the rest blank, and clicks Save All.

Yellow highlight. Clicking a face on the video canvas draws a yellow bounding box overlay and highlights the corresponding row in the enrollment form, making it clear which face is being named.

Chapter 04

Conclusion

FaceRecServer demonstrates a complete, production-shaped face recognition pipeline built entirely with open-source tools in a short hackathon timeframe. The system meets every requirement in the brief — camera access, embedding-based recognition, structured storage, visual feedback, deployment, and CI/CD — and adds meaningful innovations: live enrollment with no offline training, multi-person enrollment in a single interaction, and a polished streaming UI.

The most significant technical decision was abandoning LBPH in favour of dlib embeddings. LBPH would have satisfied the minimum requirements, but the switch to a pretrained ResNet model delivered substantially higher accuracy, eliminated the offline data-collection workflow, and made live enrollment possible. The cost was a more complex Docker image (dlib requires cmake and C++ build tools) and one runtime compatibility issue with pkg_resources, both of which were resolved.

The architecture — browser captures frames, server processes and annotates, WebSocket streams the result back — scales naturally. The server is stateless per-frame and thread-safe; the embedding database is a plain JSON file that any future version of the system can read. Replacing the recognition backend (for example with ArcFace or FaceNet for even higher accuracy) requires changing only inference.py — the rest of the stack is unaffected.

Open-source stack face_recognition, Flask, SocketIO, OpenCV, dlib — all freely available, battle-tested libraries. No vendor lock-in.
Swappable backend Replacing dlib with ArcFace or FaceNet requires changing only inference.py. The WebSocket layer, UI, Docker stack, and CI/CD are unaffected.
Thread-safe by design threading.Lock guards the frame buffer and JSON writes. Multiple SocketIO threads can process events concurrently without race conditions.
Portable data face_embeddings.json is plain JSON. It can be versioned, backed up, migrated, or extended without touching any code.
